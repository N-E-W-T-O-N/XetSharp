# XetSharp

.NET interop bindings for [xet-core](https://github.com/huggingface/xet-core) — HuggingFace's
content-defined chunking, deduplication, and CAS upload engine (`hf-xet`).

The goal is to bring `hf-xet`'s chunked upload/download to the .NET ecosystem by wrapping the
Rust `xet-core` crates behind a C ABI and calling them from C# via P/Invoke, instead of the
plain-HTTP path the current .NET Hub clients use.

## Layout

| Path | What it is |
|------|-----------|
| `src/lib.rs` | Rust `cdylib` — the C-ABI shim over `xet-core` |
| `Cargo.toml` / `build.rs` | Rust build + `csbindgen` C# binding generation |
| `xet-core/` | Git submodule (pinned to `v1.6.0`) — the upstream Rust engine |
| `XetSharp/` | The C# library. `Native/NativeMethods.g.cs` is generated by `csbindgen` |
| `XetSharp.Example/` | Console app exercising the bindings |

## ⚠️ Target system: .NET is portable, Rust is not

This is the key thing to understand about building this project.

**The .NET side builds once and runs anywhere.** `dotnet build` produces platform-agnostic IL
(intermediate language). The same `XetSharp.dll` assembly runs on Linux, Windows, and macOS as
long as a compatible .NET runtime is installed.

**The Rust side must be compiled per platform + architecture.** `cargo build` produces a *native*
shared library — machine code for one specific OS/CPU. There is no universal binary; each target
needs its own compile, and each produces a differently-named file:

| Platform | Rust target triple | Native library name |
|----------|-------------------|---------------------|
| **Linux x64** (current focus) | `x86_64-unknown-linux-gnu` | `libxetcore_native.so` |
| Windows x64 | `x86_64-pc-windows-msvc` | `xetcore_native.dll` |
| macOS Apple Silicon | `aarch64-apple-darwin` | `libxetcore_native.dylib` |
| Linux ARM64 | `aarch64-unknown-linux-gnu` | `libxetcore_native.so` |

Because of this, a XetSharp package that ships to multiple platforms must bundle **one native
library per target** (typically under a `runtimes/<rid>/native/` folder), while the managed
assembly is shared across all of them. At runtime .NET's loader picks the correct native library
for the host it's running on.

### Current scope: Linux x64 only

For now this repo targets **`x86_64-unknown-linux-gnu`** only. `cargo build` produces
`target/debug/libxetcore_native.so` (or `target/release/…` with `--release`). Other targets
(Windows `.dll`, macOS `.dylib`) are not yet wired up.

> Note: `XetSharp/XetSharp.csproj` currently references `xetcore_native.dll`/`.pdb` (Windows
> names). On Linux x64 those includes won't match the produced `.so` and will need updating as
> part of the cross-platform packaging work.

## Getting started (Dev Container)

The `.devcontainer/` sets up a Linux x64 environment with both toolchains:

- .NET SDK 10 (`ghcr.io/devcontainers/features/dotnet:2`)
- Rust latest stable (`ghcr.io/devcontainers/features/rust:1`)

On creation it initializes the `xet-core` submodule, then runs `cargo build` and
`dotnet restore`. Open the folder in VS Code and choose **Reopen in Container**, or use the
`devcontainer` CLI.

## Building manually

```bash
# 1. Fetch the upstream engine
git submodule update --init --recursive

# 2. Build the native shim (Linux x64 -> target/debug/libxetcore_native.so)
cargo build

# 3. Build / run the .NET side
dotnet build XetSharp.sln
dotnet run --project XetSharp.Example
```

`XetSharp.csproj` copies the native lib into a NuGet-style `runtimes/<rid>/native/` folder in the
output and flows it to referencing projects, so `dotnet run --project XetSharp.Example` works after building
the Rust side.

### Cross-compiling for linux-arm64

The .NET side is portable, so only the Rust `.so` needs cross-building. `cargo-zigbuild` handles it
in one container — including the `aws-lc-sys` C/assembly crypto dependency (verified: produces an
AArch64 ELF). One-time setup, then build:

```bash
# setup (once)
apt-get install -y cmake python3-pip
python3 -m pip install --break-system-packages ziglang
cargo install cargo-zigbuild
rustup target add aarch64-unknown-linux-gnu

# build both Linux targets into the runtimes/<rid>/native layout
./scripts/build-native.sh x64 arm64
dotnet publish XetSharp.Example -c Release -r linux-arm64 --self-contained false
```

The csproj has a `<Content>` row per target (each `Condition=Exists`), so a checkout with only one
`.so` built still works. Because the native libs are loose `Content` (resolved at runtime by
`NativeMethods.Loader.cs`), a RID-specific publish currently carries every built RID's `.so` rather
than trimming to the target — harmless, and proper trimming comes with NuGet `runtimes/` packaging.

### Native library loading

`XetSharp/NativeMethods.Loader.cs` registers a `NativeLibrary.SetDllImportResolver` (via
`[ModuleInitializer]`) that resolves the `xetcore_native` import to the correct per-platform file:

```
runtimes/<rid>/native/libxetcore_native.so     # linux-x64, linux-arm64, ...
runtimes/<rid>/native/xetcore_native.dll        # win-x64
runtimes/<rid>/native/libxetcore_native.dylib   # osx-arm64
```

It falls back to a flat copy next to the assembly, then to the OS default search. The resolver is
compiled only for `net5.0+` (`#if NET5_0_OR_GREATER`) since `NativeLibrary` does not exist on
`netstandard2.1`; consumers on that target rely on default probing or register their own resolver.
To add a platform, cross-build the Rust crate for that target (e.g. with `cargo-zigbuild` for
Linux/Windows targets, or a macOS runner for `osx-*`) and add a matching `<Content>` row producing
the `runtimes/<rid>/native/` artifact.

## Packaging (NuGet)

To avoid shipping every architecture's native binary in one download, XetSharp uses the
**split / runtime-package** model: a small meta package plus one native package per RID.

| Package | Contents |
|---------|----------|
| `XetSharp` | managed assembly (`lib/net10.0`, `lib/netstandard2.1`) + `runtime.json` — **no native** |
| `XetSharp.runtime.linux-x64` | **only** `runtimes/linux-x64/native/libxetcore_native.so` |
| `XetSharp.runtime.linux-arm64` | **only** `runtimes/linux-arm64/native/libxetcore_native.so` |

The `runtime.json` in the meta package is a runtime graph: on restore, NuGet pulls in **only** the
`XetSharp.runtime.<rid>` package matching the consumer's RID — a `linux-x64` app downloads no
`arm64` bytes, and vice versa. Build them with:

```bash
./scripts/pack.sh        # release-builds natives (x64 + arm64) and packs all three into ./artifacts
```

Native binaries are release-built and stripped (≈8–10 MB each, vs ~164 MB debug). The meta
package's dev-only `<Content>` native rows are marked `Pack="false"`, so they never leak into it.

> **Consumer requirement:** with split packages the app must specify a RID (`<RuntimeIdentifier>`
> or `dotnet publish -r <rid>`) so NuGet resolves the runtime package. A framework-dependent build
> with no RID won't pull a native. (If you'd rather trade download size for zero-config, a single
> universal package that bundles all RIDs is the alternative — publish still trims to one RID.)

## Usage

```csharp
using XetSharp;

var client = new XetClient();

// Optional: route xet-core's tracing output to a file (level via XET_LOG env var, default info).
client.InitLogging("xetsharp.log");

// Local CAS: chunk + dedup + write xorbs/shards into a directory (no network/auth).
string uploaded = client.UploadFile(casDirectory: "/tmp/cas", filePath: "model.safetensors");
// uploaded => {"hash":"...","file_size":...,"sha256":"...","metrics":{...}}

// Reconstruct the file from its Merkle hash.
string restored = client.DownloadFile(casDirectory: "/tmp/cas", hash: "<hash>", destPath: "out.safetensors");
// restored => {"bytes_written":...}

// Remote CAS (e.g. HuggingFace Hub): chunk + dedup + push, authenticated with a token.
string remote = client.UploadFileRemote(
    endpoint: "https://cas-server.huggingface.co",
    token: "<cas-jwt>",
    filePath: "model.safetensors",
    repo: "user/model",        // optional
    tokenExpiration: 0);       // epoch seconds; 0 = use token as-is

// ... and the matching remote download:
client.DownloadFileRemote("https://cas-server.huggingface.co", "<cas-jwt>", "<hash>", "out.safetensors");

// Long-running session: supply a refresh callback; xet-core calls it when the token nears expiry.
client.UploadFileRemote(
    endpoint: "https://cas-server.huggingface.co",
    token: "",                                   // may be empty; the callback provides it
    filePath: "model.safetensors",
    tokenRefresh: () => (FetchFreshJwtFromHub(), DateTimeOffset.UtcNow.AddMinutes(15).ToUnixTimeSeconds()));
```

Upload calls return JSON with the file's Merkle `hash`, `file_size`, `sha256`, and deduplication
`metrics`; download calls return `{"bytes_written":N}`. `XetSharp.Example/Program.cs` is a runnable demo
(upload → download round-trip + logging; set `XET_ENDPOINT` / `XET_TOKEN` / `XET_REPO` env vars to
exercise a real remote upload).

## How the binding is built

- `src/lib.rs` is a small C-ABI shim over `xet_data`'s `FileUploadSession` / `FileDownloadSession`.
  It follows three FFI safety rules: no panic crosses the boundary (`catch_unwind`), async is
  bridged to sync at the edge (`runtime.bridge_sync`), and returned strings are caller-freed
  (`xet_string_free`).
- `build.rs` runs `csbindgen` at `cargo build` time to (re)generate `XetSharp/Native/NativeMethods.g.cs`.
- `XetSharp/Client.cs` wraps the generated P/Invoke calls with UTF-8 marshalling and error handling.

## Demo CLI

`XetSharp.Example` runs a self-contained round-trip demo, or takes a command so you can drive the engine:

```bash
dotnet run --project XetSharp.Example -- upload   <casDir> <file>
dotnet run --project XetSharp.Example -- download <casDir> <hash> <dest> [size]
dotnet run --project XetSharp.Example                     # upload -> download round-trip demo + logging
```

## Testing

`XetSharp.Tests` is an [xUnit v3](https://xunit.net) project. Every test crosses the P/Invoke
boundary into the native engine, so a green run verifies the **interop** itself — marshalling, the
async bridge, error propagation, and memory ownership — not just the managed code.

```bash
cargo build                                      # produce the native .so first
dotnet test XetSharp.Tests/XetSharp.Tests.csproj # 7 tests: upload, download round-trip, dedup,
                                                 # error codes, remote marshalling, logging
```

## Status

**Working (verified end-to-end through the .NET binding on linux-x64):**
- **Local upload + download round-trip** — content-defined chunking, dedup, xorb/shard
  serialization, and byte-exact reconstruction from a Merkle hash.
- **Remote upload + download** — `UploadFileRemote` / `DownloadFileRemote` talk to a CAS endpoint
  (e.g. the HuggingFace Hub) using a caller-supplied bearer token. Same engine, different transport.
- **Automatic token refresh** — an optional `TokenRefreshCallback` (a C# delegate) is marshalled
  across FFI via `SetDllImportResolver`-style function pointers; xet-core invokes it when the token
  nears expiry (verified: the callback fires across the boundary). Net5+ overloads.
- **File logging** — `InitLogging` routes xet-core's `tracing` output to a file (level via `XET_LOG`).
- **Cross-platform loading** — `SetDllImportResolver` over a `runtimes/<rid>/native/` layout.
- **linux-x64 + linux-arm64** — native lib builds for both (arm64 cross-compiled with
  `cargo-zigbuild`, incl. `aws-lc-sys`); csproj emits both into `runtimes/<rid>/native/`.
- **Split NuGet packaging** — meta `XetSharp` + per-RID `XetSharp.runtime.<rid>` packages via
  `runtime.json`, so consumers download only their arch (`scripts/pack.sh`).
- **xUnit v3 interop tests** — 7 tests crossing the FFI boundary (`XetSharp.Tests`), all passing.
